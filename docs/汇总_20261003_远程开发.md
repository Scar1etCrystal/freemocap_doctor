## 2. 任务1：多 agent 并发安全

**问题**：所有 agent 共用一个全局 `version`；读工具内部的 `frame_set` 也会触发 depsgraph 回调把它推高。
3–5 个 agent 同时干活时，`expect_version` 几乎每次都过期——agent 互相"误伤"、反复重读。

**设计**（咨询性租约，不是锁；GUI 里的用户永远不受限）：

| 机制 | 行为 |
|---|---|
| `claim {agent_id, bones/chain, frames, ttl_s}` | 同骨 + 帧重叠的别人 → 不批（给出占用者、重叠帧）；父子骨重叠 → 批 + related 警告（`strict` 则不批）；`check_only` 只查；TTL 15 min，活动即续期 |
| 写入检查 | 每个写工具都有 scope（旧工具解析参数；插件工具 `WRITE_SCOPES`；reapply/revert/set_influence 用 op 实际写过的骨）。落在别人 claim 里 → `E_CLAIMED`；空闲 → 自动认领 |
| scope 化 `expect_version` | 写入日志记 (version, owner, 骨, 帧)；过期仅当期间**别人**改了**同骨或祖先骨**且帧重叠，或发生外部（GUI）编辑；否则放行并在 warnings 说明。读工具保持严格 |
| 版本只因真实改动而变 | 工具执行期间屏蔽 depsgraph 回调；拖时间轴/播放不算编辑；写工具成功后显式 +1 |
| owner | op 记录 `owner`；别人 revert/reapply/set_influence → `E_OWNER`；`ab_toggle(agent_id)` 只拨自己的轨 |
| `plan_scopes`（派单时天然避开） | 协调者把计划的任务 scope 先过一遍：两两 hard/related 冲突、与现有租约冲突、建议并行批次（父骨任务先做、同骨重叠不同批） |

纯逻辑在 `agent_claims.py`（无 bpy，`tests/test_agent_claims.py` 覆盖）。e2e_concurrency 34/34：
抢同一 scope 只批一个；4 个线程 agent 经真 socket 各写 3 次、链式 expect_version、零误报；祖先骨被改 →
子骨 owner 收到 E_STALE；读工具不再推高版本；派单批次 `[[spine, head-later], [armL, armR], [handL-late]]`。

## 3. 任务2：性能（结果零数值变化）

**尺子**：`tests/bench_baseline.py` 一遍里既计时（经 `_dispatch`，含桥开销）又录 golden——读结果、op 参数/
指标、写出的 delta 关键帧、受影响骨的求值矩阵，共 23 节；`bench_compare.py` 按**精确浮点相等**比对。
同一份代码跑两遍 golden 逐位一致（尺子本身可信）。

**测量先行**（cProfile）：`frame_set` 占 hold_pose/reapply/probe/烘焙的 80–88%。猜测"281 个网格变形
是大头"被实测否定（隐藏全部网格只快 8%，结果逐位一致但不值得改用户可见状态）——瓶颈是 RIG 自身
503 个 Rigify 约束。所以策略是**少求值**，不是求值更快：

| 优化 | 做法 | 为什么逐位一致 |
|---|---|---|
| socket 泵 | headless 主循环改为等 socket 线程的 Event（原：固定 70 ms 轮询）；GUI 定时器忙时 5 ms 复查；客户端 list+join 收包 | 只改调度时机 |
| 信号库 | 键从数据版本改为"外部改动纪元"——agent 写 delta 改变不了它的输入（npz 缓存+标注区间+设置），重建结果本来就逐位相同 | 输入相同 |
| 四元数乘法向量化 | `swing_twist_deg`/`delta_quat` 的逐帧 Python 循环 → `_qmul_rows` | 同一表达式、同一求值顺序、numpy ufunc 不做 FMA 合并 |
| probe_anatomy 单遍 | 原来对同一组采样帧扫 4 遍（方向/局部主轴/次轴/toward 误差）→ 1 遍；原版保留为 `_probe_slow` 兜底（owner 骨随帧变化时） | 同帧求值确定 |
| hold_pose 多骨 world_dir | 每骨各扫一遍 → 所有骨一遍；probe 轴每帧算一次共享 | 同上；单骨数学逐字搬入 |

基准表（中位数，ms）见 §3.1（会话末尾补：原始 commit 与最终代码各跑多遍取中位）。
golden：除 `clean_jitter`、`effect_check` 两节（§7 的有意修复）外**全部逐位一致**。

**"自动修复部分"（向导步骤）**：fixture 处于第 9 步、所有步骤已提交，恢复到步骤前所需的检查点在用户
Windows 盘上，套件里没有——无法在这里重跑、无法建 golden，按"任何数值变化=回滚"的铁律没有盲改
（见 §11）。仓库里 56 个纯 Python 单测在向量化后全部通过。

## 4. 任务3：`motion_copy`（+ 验收工具 `compare_motion`）

- 源 = 当前**可见**姿态（含已有修复），先采样后写入（源窗与目标窗同骨重叠也精确）。
- `space="local"`（默认）复制关节局部旋转——随目标时刻的身体朝向走，时间平移和镜像手势都对；
  `space="world"` 按 GOAL 原规格"世界镜像（X=0，前方 −Y）后转目标骨局部"，人转了身就不跟身体走。
- 镜像不靠猜局部公式：`F = Rest_src⁻¹·S·Rest_dst`（S = X 反射），局部镜像 `Basis_dst = F⁻¹·Basis_src·F`
  ——由"世界镜像 + 父骨同样镜像"严格推导，rest→rest 精确；本 RIG 左右骨 F 与 diag(−1,1,1) 相差 <2e−5。
- `bone_map` 跨部位、`dst_range` 时间缩放（slerp 重采样）、`mode="add"` 叠加、`channels="rot+loc"`。
- delta 相对可见姿态计算 → 叠在别的修复上也精确（旧工具相对基底动作，是"近似叠加"）。
- 实测：时间平移 0.00005°；镜像 local 19 骨（含 YXZ/XYZ Euler）0.0045°（胸骨系掌心镜像 0.005°）；
  world 镜像左右掌心 X 镜像 0.000°；时间缩放两端 0.00002°；add 0.00077°；窗外/revert 0.00000°。
  四元数骨有 ~0.005–0.03° 的 NLA float32 噪声底，验收阈值别设得比 0.03° 更低。

| `follow_through` | stop 后沿接近轴的衰减正弦，amount 定义为第一瓣/幅度（形状归一化）；`propagate` 让链末端逐级晚起振 | 瓣 +12.83/−6.59/+2.85/−0.46°（第一瓣目标 13.12°），stop 前 0.0000° |

## 6. 自由加的工具：脚滑

## 10. 对整体设计的意见（按影响排序）

1. **delta 的参照系要统一到"可见姿态"。** 新工具都相对当前可见姿态算 delta，叠在别的修复上是精确的；
   旧的 hold_pose/clean_jitter/restore_accent 相对**基底动作**算（手册里叫"stacking 近似"）。两套语义
   并存，agent 很难推理"我这条修复叠上去到底是什么"。建议把旧工具迁到 `agent_pose`（采样可见姿态 →
   `pose_deltas`），golden 会变，所以单独一个版本做。代价是**顺序依赖**：下层修复被 reapply/revert 后，
   上层 delta 就不再精确——需要记录"同骨同帧段的上层 op"，并给一个 `reapply_chain` 一键按顺序重算。
2. **信号库冻结在第一次烘焙。** describe/get_series/get_joint_angles/validate/fix_ground 读的是 npz 快照，
   修完不变——agent 最容易在这里误判"没写上"然后叠第二层修复。现在靠提示词"快照类 vs 实时类"兜住；
   长期应二选一：写入后对受影响帧段增量重烘（信号库变成"当前"），或把两类工具改名/加 `source:"original"|"live"`
   参数，让语义写在调用里而不是靠记忆。fix_ground 用快照里的脚底高度，修过 foot_lock 之后会算错，属于同一问题。
3. **每个 op 一条轨，会越积越多。** 工作文件里已有 103 条空的 `NlaTrack.xxx` 轨（来源不明，疑为旧迁移/
   GUI 下推遗留）+ 15 条修复轨。轨越多每帧 NLA 求值越慢、面板越乱。建议：①清理空轨的维护工具；
   ②用户 commit 后提供"把已确认修复烘进一条 per-bone strip"的合并操作。
4. **IK/FK 要成为工具的一等公民。** 腿是 IK，FK 腿骨有 key 但写了看不见；膝朝向的 owner 却是 thigh_fk。
   现在靠报错/提示词告知。更好的是让工具自己映射：腿部请求自动落到 foot_ik（+膝 pole 目标）。
5. **骨架语义层值得单独一层。** 这次 overlap、motion_copy、并发的祖先判断都需要"语义父骨"（穿透 Rigify
   的 MCH/ORG/COPY_TRANSFORMS）。`agent_pose.semantic_parent` 现在是启发式 + 脊柱特例；建议在 rig_bake_spec
   旁边维护一张显式的"控制骨层级表"（每种 rig profile 一张），并由 e2e 校验。
6. **性能的地板是 RIG 求值（~1.9 ms/帧，503 个约束）。** 再往下快只能更少求值：同一批请求里缓存
   (版本, 帧) → 可见姿态采样；或给采样专用一个只含 RIG 的 view layer。网格不是瓶颈（实测隐藏全部网格仅快 8%）。
7. **参数校验风格要统一。** motion_copy 拒绝未知参数（拼错 `mirorr` 直接报错），principles/overlap 只在
   warnings 里提示。对能力较弱的模型，**拒绝 + 给出最接近的合法参数名**更安全；建议统一成拒绝。
8. **数据目录存绝对路径本身就脆弱。** 这次修的是症状（外系统路径不信任）。更稳的是 .blend 里存相对 blend
   的路径，只在用户自定义目录时存绝对路径。
9. **远程测试与服务抢唯一的 Blender 名额。** 8 GB 机器上服务开着就跑不了 e2e。可以给 bridge 加一个
   只在 headless 测试模式开放的 `run_e2e` 工具，在服务进程内跑测试（新 Blender 进程不再需要）。
   另：实测单个 Blender 峰值 0.7–1.2 GB，比 GOAL 里估的 1.5–2.5 GB 小，内存规则可酌情放宽到 2 个。
10. **向导的自动修复步骤需要可复现的 fixture。** 现有 fixture 停在第 9 步、检查点不在套件里，导致这部分
    性能无法测量/验证。建议随套件附一个"第 0 步"的 fixture（或各步骤前检查点）。
11. **strip 名里带上 owner。** 现在 owner 只在 op 日志里；GUI 的 NLA 编辑器里看不出是哪个 agent 写的。
    多 agent 时值得把 agent_id 缩写放进 strip/轨名（注意 is_agent_track_name 依赖 `agent_` 前缀）。
